# Concurrency: what holds on any machine

Generated by `python scripts/generate_results.py`. Do not edit by hand.

Absolute timings live in `results/concurrency-raw.md`, which is
gitignored: `asyncio.sleep` overshoot is machine-dependent, so
committing millisecond values makes CI fail on a different runner
for no useful reason. The claims below are the portable ones.

- Tasks: 128, target service time 20 ms
- Limits swept: 1, 2, 4, 8, 16, 32, 64, 128
- Reproduce: `python scripts/generate_results.py`
- Deterministic: fixed service time, no randomness

## 1. Service time does not depend on the concurrency limit

Across a 128x range of concurrency limits,
measured p95 service time stays within **25%** of its maximum.
This script asserts it and exits non-zero if the claim breaks.

Service time is a property of the work. The limit cannot change it.
Everything else a caller observes is admission delay.

## 2. Which resource bounds the run

Reported as order-of-magnitude bands, not raw ratios: the exact value
carries timing noise and would make this file differ on every run.

| limit | queued vs service | bound by |
|---|---|---|
| 1 | >50x | admission |
| 2 | >50x | admission |
| 4 | 10-50x | admission |
| 8 | 10-50x | admission |
| 16 | 2-10x | admission |
| 32 | 2-10x | admission |
| 64 | ~1x | **crossover** (flips between runs) |
| 128 | <1x | service |

The crossover is the useful number: below it you are waiting for a
slot, above it you are waiting for the backend. **The two are fixed
by opposite actions** -- raise the limit and shed load, versus buy a
faster backend. A single latency figure cannot tell you which.

## 3. p95 tracks the number of sequential waves

With N tasks and limit L, work proceeds in ceil(N/L) waves, so p95
total should approximate `waves x service`.
Observed p95 stays within **2x** of that model across the whole
sweep -- asserted here -- confirming the semaphore serialises work
rather than dropping or duplicating it.

## Limitations

- **Simulated backend, not a live endpoint.** The claim under test is
  about this client's admission control; real API variance would swamp
  it. These numbers predict nothing about any real provider.
- `asyncio.sleep` is a lower bound on real I/O: no connection-pool
  contention, no TLS, no DNS, no HTTP/2 head-of-line blocking.
- Single machine, single event loop, single process.
